## 1. 项目是什么、为什么自研

**目标**：在**消费级硬件**上跑 DeepSeek-V4-Flash（总权重 156GB 级）。
本机只有 **RTX 5070 12GB + 32GB DDR4**；云端给的是 **4 × 51.5GB 的 RDNA3 卡**（无 FP8/FP4 矩阵硬件）。

**做法**：不依赖 vLLM / llama.cpp，自研「**三层缓存 + 43 层窗口流水**」引擎 —— 权重按需从磁盘搬到 GPU，
以「**活性专家**」为粒度做缓存，让 12GB 卡也能把 156GB 的模型跑起来。

**和公共实现（llama.cpp / vLLM）的关系**：

| | llama.cpp 的 `--n-cpu-moe` 路线 | 本引擎 |
|---|---|---|
| 粒度 | 按**层**决定放 CPU 还是 GPU | 按**专家**做缓存（单专家 12.75MB） |
| 缓存 | 无专家级 LRU（近版本才有 RFC 在讨论） | **磁盘 → RAM LRU → GPU 热池 → 显存仓库** 四级 |
| 调度 | ggml 图 | 自研：43 层窗口流水 + 在线分块注意力 + MTP |
| 可借鉴处 | 通用、成熟 | **专家级缓存容量规划 / 命中率 / 搬运带宽** 的实测数据（第 8~9 章） |

> 本项目的价值不在"又写了一个引擎"，而在**同一台机器上把"MoE 专家搬运"这条路径的每个环节都量了一遍**：
> 命中率为什么会归零、GIL 怎么把拷贝吞吐砍掉 3.5~7 倍、4 卡为什么只有 2.1×、天花板在哪 ——
> 这些数字对任何做 MoE offload 的人都有用（含 llama.cpp 社区正在讨论的"热专家显存缓存"RFC）。

## 2. 环境对照

| | 本机（基线） | 云端（移植目标） |
|---|---|---|
| GPU | RTX 5070 12GB（CUDA 12.8） | **4 × AMD Radeon / gfx1100（RDNA3）**，每卡 51.5GB，CU=96，P2P 可用 |
| CPU / 内存 | i5-14600KF / 32GB DDR4 + 大页文件 | EPYC 9334 / 32 核；容器 **cgroup 上限 118GB，`oom.group=1`**（超了连 sshd 一起杀） |
| 模型 | FP8 版 **274GB**（F32 block scale） | FP4 版 **148.65GB**（专家 `I8` = packed E2M1，scale `F8_E8M0` group-32） |
| PyTorch | CUDA 12.8 build | **容器自带 torch 2.9.1 + ROCm**（全程 `--no-deps` 保护，绝不重装） |
| transformers | 5.15.0 | 5.16.1 |
| Python | — | 3.12（快照里的 `cpython-312` pyc） |
| 引擎 | `v4flash_chunked_sched.py`（三层缓存 + 窗口流水） | **同一份代码** + 下列 ROCm 适配 |

**硬件事实（实测，不是规格表抄来的）**：

- `rocminfo` 报 **每卡 96 CU**；torch 报 48 —— 那是 **WGP 口径**（1 WGP = 2 CU）。
  SIMDs/CU = 2、Wavefront = 32 → 每卡 **192 个 SIMD32 单元**。
- **RDNA3 没有专用矩阵核**（无 CDNA 的 MFMA / 无 Tensor Core 对应物），**也没有 FP8/FP4 浮点矩阵支持**。
  唯一的矩阵指令是 WMMA（16×16 tile，仍是全 wave 跑在 SIMD 上）。
  → 这解释了后面第 7 章"纯 PyTorch 反量化没损失多少"：**反正本来就没有 FP8 硬件可失**。
- 互联：**P2P 可用但走 PCIe（2 hops）**，实测双向 20~28GB/s；**无 XGMI**。

## 3. 引擎架构详解

### 3.1 文件

| 文件 | 作用 |
|---|---|
| `engine/v4flash_chunked_sched.py`（80KB，主体） | 配置/权重读取、层构建、窗口流水 forward、MoE（活性专家）、采样、MTP、专家仓库 |
| `engine/v4flash_chunked_server.py` | HTTP 服务（`8123 /v1/chat/completions`，OpenAI 兼容、SSE 流式、记忆召回、工具调用） |
| `engine/v4flash_chunked_attention.py` | 在线分块注意力补丁（query 块 256 / KV 块 512，超 1024 token 触发，支持 1M 上下文） |
| `engine/v4flash_agent.py` / `v4flash_tools.py` / `v4flash_sched.py` | agent / 工具调用支持 |

### 3.2 三层缓存（核心思想）

```
模型文件（safetensors 46 分片，FP4 版 148.65GB）
   │  pread（绕开 mmap，按张量偏移直读；per-thread 文件句柄 + header 缓存）
   ▼
① RAM 专家 LRU（OrderedDict，V4F_LRU_ITEMS）
   │  H2D（12.75MB/专家）
   ▼
② GPU 显存：热池（V4F_GPU_EXP_MAX）──溢出下沉──▶ 显存仓库（V4F_EXP_STORE_DEV 指定的卡）
   │
   ▼
③ 43 层非专家权重：窗口流水（K=8 层驻留 → 算完 D2H 回 pinned → 下一窗口 H2D 预取）
      ※ 云端 51.5GB 卡：改为 **43 层全部常驻**（V4F_RESIDENT_LAYERS=1），彻底不搬

KV cache：GPU 上的 DynamicCache（单头 MQA + 压缩层，compress_ratios 4/128；1M 上下文 ≈ 1GB）
```

**查找顺序**：`GPU0 热池 → GPU1/2/3 仓库 → RAM LRU → 读盘`。
命中仓库时**把那个专家（12.75MB）拉回计算卡**（计算永远在 GPU0）。

### 3.3 关键设计点（每条都对应一个踩过的坑）

- **权重加载**：`_build_template` 在 meta 设备建结构 → `to_empty(device='cpu')` 实体化 → `load_state_dict(assign=True)` 注入。
  ⚠️ **这正是第 5 章 NaN 事故的埋点**：`to_empty` 会把 `persistent=False` 的 buffer 变成**未初始化内存**，
  而 state_dict 里没有这些 key → RoPE 的 `inv_freq` **从未被写入**。
- **MoE**：`V4LazyMoE` 手写专家 GEMM（gate/up/down = w1/w3/w2），top-k 路由，全程 fp32 激活，
  用 `swiglu_limit` 模拟 FP8 激活范围。
- **流式 prefill**：超长输入按 `prefill_chunk_size` 分段过层，KV 跨段累积（数学等价全量）。
- **MTP**：`V4MTPModule`（mtp.0 权重）一级预测 + 拒绝采样（置信度 < 0.5 拒绝并回滚 MTP cache）。
  实测：30 步生成**额外产出 12~30 token（≈1.4~2×）**。
- **采样**：`temperature / top_k / top_p / repetition_penalty`；额外加了 **NaN 防御回退 greedy**
  （定位期用，根因修掉后留作保险）。
- **服务端**：`V4F_KEEP_GPU_CACHE=1` —— 请求结束**不清** GPU 专家缓存，跨请求复用。

### 3.4 显存账的真相：开销全是"权重"，不是"计算图"

| 项 | 大小 | 说明 |
|---|---|---|
| 单层权重 | **0.3GB** | 43 层合计 13GB |
| 单层激活（decode 1 token, fp32） | **~2~4MB** | q/k/v + MoE 中间量 |
| 1 个专家权重 | **12.75MB** | 一次命中 = 一次 0.65ms 的 P2P 拷贝（或 RAM ≈0.5ms） |
| KV cache | 1M 上下文 ≈ **1GB** | 单头 MQA + 压缩层 |
| embed + lm_head 常驻 | **3.2GB** | bf16 |

→ 「多路并发」在显存上几乎不花钱（每路多几 MB 激活 + 自己的 KV），**瓶颈是算力与专家搬运带宽**。

## 4. 模型格式：两套 checkpoint 的差别（ROCm 适配的第一道坎）

| | 本机 FP8 版（274GB） | 云端 FP4 版（148.65GB） |
|---|---|---|
| 非专家层 | `F8_E4M3` + **F32** block scale(128×128) | `F8_E4M3` + **`F8_E8M0`**（UE8M0）block scale(128×128) |
| 专家层 | `F8_E4M3` + F32 block scale | **`I8` packed E2M1（MXFP4）** + `F8_E8M0` group-32 |
| 引擎路径 | 官方 CUDA FP8 kernel | 纯 PyTorch 反量化（`V4F_TORCH_FP8=1`） |
| 每个专家 | 25MB | **12.75MB**（w1/w2/w3 各 4MB + 各自 scale 0.25MB） |
| 全量专家 | 11008 个（43 层 × 256） | 同 = **≈140GB**（这个数字决定所有容量规划） |

**MXFP4 解码实现**（与官方逐位等价，已实测）：

```python
# I8 packed E2M1：低 nibble = 偶数列 → 16 值 LUT（0,0.5,1,1.5,2,3,4,6 及负数）
# scale F8_E8M0 → 2^(byte-127)，用 (exp << 23).view(float32) 位转，等价官方 scales-127 + ldexp
```

**ROCm 适配清单（相对本机基线的最小增量）**：

1. **FP8 kernel 缺失** → `_TorchFP8Kernel` 纯 PyTorch stub：`_dequant_linear()` 按 block 反量化后 `F.linear`；
   同时把 `transformers.integrations.finegrained_fp8.load_finegrained_fp8_kernel` 换成 stub（`V4F_TORCH_FP8=1` 强制走）。
2. **FP4 专家支持**：新增 `_dequant_mxfp4()`；`fp8_matmul()` 按 `w.dtype == torch.int8` 分派到 MXFP4 分支。
3. **scale dtype**：`DTYPE_MAP` 增加 `F8_E8M0 → torch.float8_e8m0fnu`。
4. **线程数 / 缓存容量全部 env 化**（`V4F_EXP_WORKERS / BUILD_WORKERS / D2H_WORKERS / LRU_ITEMS / GPU_EXP_MAX / MTP / MAX_SEQ ...`）——
   这是能在云端快速做 A/B 的前提。
5. 采样路径加 NaN 防御（第 5 章）。
6. `V4F_KEEP_GPU_CACHE=1` 跨请求保留 GPU 专家缓存。

## 5. ★ 事故一：NaN / 空输出（"同一份权重时好时坏"）

### 5.1 症状

- 请求返回**空文本**（SSE 只有 `{"done":true}`），日志每 token 刷 `[warn] probs NaN/Inf, 回退 greedy`。
- **时好时坏**：同配置同 prompt 跑多次结果翻转；首发 NaN 的层在 layer 3 / layer 24 / 5,25,35 之间**跳**。
- **本地同款代码不报错**（这是最误导人的一点）。

### 5.2 定位过程（每一步都先实测，逐个排除）

| 假设 | 实测 | 结论 |
|---|---|---|
| 权重污染 / 下载坏 | 全量扫 **34167 个 E8M0 scale（8858 MB）**：字节只出现 114~127，**无 0xFF / 0xFE / 0x00** | ❌ |
| config 差异 | 本地 FP8 与云端 FP4 的 `rope_scaling / rope_theta / compress_rope_theta / head_dim / partial_rotary` **逐字段相同**；两版 transformers 算出的 `inv_freq` **逐位相同、nan=0** | ❌ |
| MTP | 已 `V4F_MTP=0`，代码注释里的"二级"未启用 | ❌ |
| 采样数学 | NaN 在 `probs.sum()` **之前**就有（logits 已 NaN） | ❌ |
| 显存 DMA / copy_stream / offload 竞态 | 常驻层、同步上传、异步上传三种模式**与是否 NaN 无相关性** | ❌ |
| **未初始化内存 / 内存复用** | canary 显示：**前向计算开始之前** rope buffer 就已带 NaN，且整轮不变 | ✅ |

### 5.3 决定性证据（三层）

```text
① 探针定位：
[nanhook]  L3 self_attn.compressor.rotary_emb out_bad=14/32 in_bad=False     ← 输入干净、输出 NaN
[nanprobe] L3 W ...rotary_emb.main_inv_freq: 非有限 15/32  max|fin|=1.811   ← inv_freq 本应 ≤1.0

② canary（把检查点放在"计算开始之前"）：
[ropewatch] W-1 前向前   5.main=2/32 25.main=2/32 35.main=2/32   ← 还没算就脏了
[ropewatch] W0  窗口算完 5.main=2/32 25.main=2/32 35.main=2/32   ← 整轮不变

③ 本地纯 CPU 复现（同款 transformers 逻辑）：
正常构造:                 [1.0, 0.7499, 0.5623, ...]
to_empty(device='cpu') 后: [0.0, 0.0, 0.0296, 0.0203, ...]        ← 初始化被抹掉
```

**受害张量的值域直接指认了来源**：`inv_freq` 应 ≤1.0，出现 **1.811** 说明里面是"别人的数据"。

### 5.4 根因（一句话）

```python
layer.to_empty(device='cpu')             # 参数/buffer 全部重建为「未初始化内存」
layer.load_state_dict(sd, assign=True)   # 参数被 sd 覆盖 ✓
```

而 `DeepseekV4RotaryEmbedding` 的 `{main,compress}_inv_freq` / `{main,compress}_original_inv_freq`
是 **`persistent=False` 的非持久 buffer —— 不在 state_dict 里 → 永远不被写入**，直接带着"上一手内存"上线：

- 云端那批内存含 **NaN 位模式**（读 148GB FP8/FP4 权重后残留的 `0xFF`）→ 该层 hidden 全 NaN → logits NaN → 空输出；
- 本地拿到的是干净页 → 只表现为 **`inv_freq ≈ 0` / 垃圾小值（RoPE 频率静默失效）** → **不报错**。
  **"本地没问题"其实是本地也中招**，只是没爆。

### 5.5 修复（最小增量，照官方 `_init_weights` 写法）

```python
elif isinstance(module, DeepseekV4RotaryEmbedding):
    for layer_type in module.layer_types:
        rope_init_fn = module.compute_default_rope_parameters
        if module.rope_type[layer_type] != "default":
            rope_init_fn = ROPE_INIT_FUNCTIONS[module.rope_type[layer_type]]
        curr_inv_freq, _ = rope_init_fn(module.config, layer_type=layer_type)
        init.copy_(getattr(module, f"{layer_type}_inv_freq"), curr_inv_freq)
        init.copy_(getattr(module, f"{layer_type}_original_inv_freq"), curr_inv_freq)
```

落地为 `_reinit_rope_buffers(mod, tag)`，覆盖**两条构建路径**：

1. `build_and_inject()` 中 `layer.load_state_dict(...)` 之后（43 层）
2. `V4MTPModule.__init__` 中 `self.load_state_dict(conv, ...)` 之后

### 5.6 验证

```text
[ropeverify:43层] rope模块=62 缓冲=248 逐位一致=248 不一致=0 含NaN=0
（62 = 41 层 compressor + 21 层 indexer.compressor）
修复后连打 6 次请求：warn_delta 全 0，输出正常（修复前约 1/2 概率空输出）
```

### 5.7 通用结论（值得发出去的那条）

> 任何"**先 `to_empty`（或 meta 初始化）再 `load_state_dict`**"的加载方式，
> 都必须显式重算**非持久 buffer**（rope / scaler / cache 类）。
> 只 load state_dict 是**不够**的：state_dict 里根本没有这些 key。
>
> 推论：**"同一份权重、有时好有时坏" → 优先怀疑未初始化内存/内存复用**，而不是数据本身
> （确定性数据问题不会翻转；会翻转的一定是状态/内存）。

## 6. ★ 事故二：LRU 抖动 —— 命中率恒为 0（最值钱的一条）

加了统计接口后当场看到：

```text
第1次请求: hot_hit=2330  store_hit=966   lru_hit=0   lru_miss=7296
第2次请求: hot_hit=4981  store_hit=2559  lru_hit=0   lru_miss=13634
```

**一次请求要摸 ~7000 个不同专家，而 LRU 只有 4000 槽位**：按"最近使用"淘汰，扫一遍 0→42 层时，
**前排刚放进去的还没回头用就被后排挤掉** → 命中率恒 0 → 每请求白读 **75GB 盘**（`/proc/<pid>/io` 的 `read_bytes` 实测）。

**修法：让三级容量 ≥ 单请求工作集（全量 11008 专家）**

| 层 | 配置 | 容量 |
|---|---|---|
| GPU0 热池 | `V4F_GPU_EXP_MAX=2200` | 28GB |
| GPU1 显存仓库 | `V4F_EXP_STORE_DEV=1` `V4F_EXP_STORE_MAX=3600` | 46GB |
| RAM LRU | `V4F_LRU_ITEMS=7000` | 89GB |
| **合计** | | **≈12800 ≥ 11008** ✅ |

效果：**读盘 75GB → 2.5GB/请求（30×）**；`lru_hit` 0 → **12399**；`lru_miss` 稳定在 7000（= 容量上限，
说明工作集已**全驻留**）。

> ⚠️ 容器 RAM 上限 118GB：RAM LRU 7000（89GB）时 anon ≈ 98GB，**别再加大**。

## 7. 性能工程：每一项改动的机制 / 收益 / 开关

### 7.1 层权重常驻（`V4F_RESIDENT_LAYERS=1`）

引擎原本按 12GB 卡设计：**每个 token 都要把 43 层权重重新 H2D 一遍**（43 × 0.3GB ≈ **13GB/token**）。
在 51.5GB 卡上启动时同步常驻 GPU0（13GB）：**请求耗时 113s → 36s**。

### 7.2 GPU1 = 纯显存仓库（计算只在 GPU0）

- 热池溢出时把最老的**下沉**到仓库（而不是丢弃）；
- 仓库命中时拉一个专家（12.75MB）回计算卡；
- **P2P 实测：12.75MB 拷贝 0.64~0.69ms，双向对称 ~20~28GB/s**（host→任一卡 26.6GB/s）。
  ⚠️ **别被首拷假象骗**：第一次测出的 22 vs 11 GB/s 是惰性初始化造成的。

### 7.3 ★ 融合 MXFP4 内核（Triton）—— "配置高却只有 1~2 tok/s"的主因

`_load_fp8_kernel()` 加载的是 **CUDA 版** finegrained-fp8 kernels，gfx1100 上必然失败 →
`FP8_KERNEL=None` → 全走纯 PyTorch 反量化：**每次矩阵乘都把权重物化成 bf16**
（`int64` 索引 LUT + 全尺寸 scale 展开 + fp32 中间张量）。

| 每次专家 GEMM [2048,4096] | 耗时 |
|---|---|
| 旧 `_dequant_mxfp4`（物化后 matmul） | **0.424 ~ 0.93 ms** |
| 只做反量化（不 matmul） | 0.389 ms（占 92%） |
| 纯 bf16 matmul（权重已反量化） | 0.033 ms |
| **Triton 融合内核（现用）** | **0.063 ms**（数值逐位一致，相对误差 0.00e+00） |

每 token 有几百次专家 GEMM → 光这一项就是 **0.3~0.4 s/token**。

实现要点（`_mxfp4_mm_kernel`）：直接读打包 int8 → 寄存器里 E2M1 反量化
（`e2m1 = 0.5m` / `2^(e-1)·(1+0.5m)` **无分支**）+ E8M0 scale（`(exp<<23)` 位转 float）→ fp32 累加。
`V4F_TRITON_FP4=1` 开启；**启动时后台预热编译**（否则首个请求卡 5 分钟，预热后只要 1 秒）。

### 7.4 分组 MoE 前向（`V4F_GROUPED_MOE=1`）

一次 `.tolist()` 摊开路由 → 按专家排序分组 → 一次 `index_select` gather → 逐组 GEMM → 一次 `index_add_` 散射。
实测**索引记账 70.3 → 2.1 ms/token（34×）**。

代价：预填退化（TTFT 20 → 38~93s，分组路径对 T 大不友好，每 token 重复读该专家整块权重）——**权衡后接受**。

### 7.5 ★ 专家重排：6 个散块 → 1 条连续记录

现状：每个专家 = 6 个分散张量（w1/w1s/w2/w2s/w3/w3s），取一个专家要 **6 次 `pread` + 6 次 `.to(device)`**
→ **每 token 拷贝调用 1260 次**。

重排成单条连续记录 **13,369,344 字节**，索引 `lid*256 + eid`：

```text
偏移        内容                          大小
0           w1.weight [2048,2048] int8    4194304 B
4194304     w1.scale  [2048,128]  e8m0     262144 B
4456448     w2.weight [4096,1024] int8    4194304 B
8650752     w2.scale  [4096,64]   e8m0     262144 B
8912896     w3.weight [2048,2048] int8    4194304 B
13107200    w3.scale  [2048,128]  e8m0     262144 B
```

- 产物：`/v4flash_expack/experts.bin` = **137.1 GB**；生成 185 秒（760 MB/s）；新实例上 145 秒（**969 MB/s**）
- 引擎：`V4F_EXPACK=<path>` 开启；`ExpertLRU.get` 返回 `(blob, 6 个视图)`，`get_expert` 用 **1 次 `.to()`** 拷整块，
  再在 GPU 上切 6 个视图 → **拷贝调用 1260 → 210 次/token**
- ⚠️ 坑：偏移表写错一次（w3.weight 终点 13312000 vs 正确 13107200）→ 报
  `shape '[2048,2048]' is invalid for input of size 4399104`。
  **改偏移表后必须拿真实张量验一遍视图。**

### 7.6 ★ 拷贝线程 6 → 3：GIL 是搬运慢的真凶

| 场景 | 聚合吞吐 |
|---|---|
| 无竞争：1 / 2 / 16 线程 | 225 / 268 / 306 专家/秒（**2 线程即封顶**） |
| **+1 个忙线程（模拟主循环占 GIL）** | 3 线程 **42** / 6 线程 **61** / 9 线程 **86** 专家/秒 |

→ 主线程跑 Python（MoE 循环）时，拷贝线程抢 GIL，**搬运吞吐掉 3.5~7 倍** ——
正好对上引擎里"每专家 8~16 ms、每 token 搬运 2.1~4.1 s"。
**降线程数 + 减拷贝次数（=专家重排）= 直接打这个点**，两项合起来就是 **0.991 → 0.454 s/token**。

### 7.7 ★★ 4 卡 = 4 个独立进程（4.01× 线性）

| | 每卡 | 聚合 |
|---|---|---|
| 1 进程 | 0.195 ms/专家 | 5,126 专家/秒 |
| 2 进程 | 0.194 ms/专家 | 10,288 专家/秒（**2.01×**） |
| **4 进程** | **0.194 ms/专家** | **20,576 专家/秒（4.01×）** |
| 对照：4 **线程**（同进程） | 0.607 ms/专家（慢 3 倍） | 仅 **1.1×** |

**结论：一卡一路可行，但必须独立进程** —— 单进程内多线程被 GIL + 进程级驱动锁串行化；
独立进程各有自己的 GIL/驱动上下文，4 卡互不干扰。

### 7.8 失败的 / 被否掉的项（同样值钱）

| 项 | 实测 | 决定 |
|---|---|---|
| 融合 epilogue（`V4F_FUSE_EPI`） | **更慢**（tm.moe 75.5s vs 38.6s） | `0` 关闭 |
| `V4F_PIN_LRU=1`（pinned 内存 A/B） | 微基准上忙线程 1.8×，但**引擎 L1175 早有结论：`wait_stream` 恒 0 → 双缓冲已隐藏 H2D，pin 不加速任何东西**，还白花 0.7s 主线程 pin_memory | **A/B 取消**（2026-09-16 用户决定） |
| `V4F_GPU_EXP_MAX=2500` | 每卡用到 44/48 GiB，**MTP 连 64 MiB 都分不出来 → OOM** | 降到 **1500** |
| 全量专家常驻显存 | 需 **140 GB/卡**（11008 × 12.75MB），远超 51.5GB | 不可行 |
| 热专家显存化（扩池） | 空闲仅 ≈16GB，扩池上限 +500~700 专家，只剩 7~10GB 给 KV，且**实测 2500 槽已 OOM** | **封口**（保留 16GB 给 KV） |

> ⚠️ `ulimit -l = 8192 KB`（8MB memlock）**并不限制 `torch.pin_memory()`** —— 它走 GPU 驱动的
> `hipHostMalloc`，不受 `RLIMIT_MEMLOCK` 管：实测 **pin 到 8GB 成功**。
> 凡是"看到参数就推断被限制"的结论，都必须跑最小验证。

### 8.5 ⚠️ 计数口径（重要，否则数字全是假的）

1. **云端服务端不返回 `usage.completion_tokens`（恒为 0）**。真实 token 数只能从实例日志取：
   ```text
   [gen] token N done (MTP+K)          → 主路径 N 个 token
   [mtp] MTP 加速统计: 额外产出 K token → MTP 又赚 K 个 → 合计 N+K
   ```
2. `tpot_test.py` 用**流式块计时**（`TPOT=(末块-首块)/(块数-1)`），**块数少时极不可信**；
   **MTP 抽中几个草稿直接决定 tok/s**（同一配置可差 2 倍）。
3. 所以：**≥10 块 + 报真实 token 数 + 注明 MTP 状态**，三件套缺一不可。
   （早先看到的 2.76~3.69 tok/s 就是"3 个块的极小样本 + MTP 抽中双草"的运气值，**不可当真**。）
4. **首个请求 ≠ 稳态**：Triton 首次编译 / 预填冷缓存能让第一个请求慢到几分钟，**第 2 个请求才是真实速度**。
5. 跨卡拷贝测速必须**逐设备** `torch.cuda.synchronize(d)` —— 不带参数只同步当前设备，会测出 15 TB/s 这种不可能值。

## 9. ★ 谁在限制速度：天花板核算

**结论：两层都在，但当下卡速度的是引擎侧；最终上限由内存链路钉死。**

### 9.1 结构性天花板（机器侧，全部实测）

- 每个 token 必须从 RAM 拉 **258 个专家 × 12.75 MB = 3.3 GB**
- RAM→GPU 实测 **26.3 GB/s**（pinned 与 pageable 同速）
  → **126 ms/token ≈ 8 tok/s 的硬上限**
- 4 个实例**共享同一条** RAM→GPU 链路 → **合计也是 ≈8 tok/s**：四卡并行**不会**把总吞吐翻 4 倍
- 越过 8 tok/s 只有两条路，都不好走：
  - **全专家常驻显存**：每卡可用 ≈48GB；非专家 149−137 = **11.6GB** + 专家 137.1/4 = **34.3GB** = 45.9GB
    → 只剩 ≈2GB 给 KV/MTP，且落在别卡的专家要跨卡搬（**15.1 GB/s < 26.3 GB/s**）
  - **热专家显存化**：按频率常驻一部分专家，直接减少每 token 搬运字节 —— **唯一现实可行的增量**（已按决定封口）

### 9.2 引擎侧离天花板还有 3.6×

```text
attn=0.354s(26%) | moe=0.926s(68%) | other=0.086s(6%) | 专家查找 258 次/token
```

- moe 里的**纯搬运提交**只要 258 × 0.194 ms ≈ **50 ms**；其余是主线程逐专家 Python 记账 +
  每专家 GEMM 派发，以及**被 GIL 拖慢的搬运等待**（线程累计 2.1~2.7 s，折墙钟 0.35~0.68 s）
- attn 0.35 s/token 与本机一致 → 是本机同款的注意力实现问题（KV 长度 + 无融合注意力内核）
- **现实可达区间 3~4 tok/s**；要 8 tok/s 必须动"专家常驻"策略本身

### 9.3 为什么"矩阵算力"不是瓶颈（附 H100 对照）

```text
计算量:  344 个专家 × 3 次 GEMM (1×4096×2048×2) ≈ 17 GFLOP
         即使只有 10 TFLOPS 有效算力 → ≈ 2 ms
搬运量:  344 次专家命中 × 0.65 ms (P2P) ≈ 220 ms     ← 真正的瓶颈
```

| | NVIDIA H100 SXM | AMD W7900 / RDNA3 (gfx1100) |
|---|---|---|
| 矩阵硬件 | 每 SM 4 个第 4 代 Tensor Core（独立单元） | **无专用矩阵核** |
| 浮点矩阵格式 | FP16 / BF16 / **FP8**（Transformer Engine）/ FP64 | **只有 FP16 / BF16**（+ 整数 IU8/IU4） |
| 矩阵指令 | mma / TMA | WMMA（16×16 tile，仍跑在 SIMD 上） |
| 显存 | 80GB HBM3 ≈ 3.35 TB/s | 51.5GB GDDR6 ≈ 0.86~0.96 TB/s |
| 互联 | NVLink ≈ 900 GB/s | PCIe P2P 实测 ≈ 20~28 GB/s |

→ 换 H100（HBM 带宽 ≈ PCIe 的 130 倍）搬运几乎免费、TPOT 能再降一个量级，
但那属于换平台 + 重写 kernel 路径。**对本引擎，先干掉搬运比换算力立竿见影得多。**

## 12. 方法论教训（这份记录里最值得抄走的部分）

1. **`to_empty()` + 非持久 buffer = 未初始化内存**；"先 to_empty 再 load_state_dict"必须显式重算非持久缓冲（rope / scaler / cache）。
2. **"同一份权重、有时好有时坏" → 优先怀疑未初始化内存/内存复用**（确定性数据问题不会翻转）。
3. **受害张量的值域能直接指认来源**（`inv_freq` 出现 >1.0 → 是别人的数据）。
4. **canary 检查点要放在"计算开始之前"**，能一次排除整条流水线。
5. **缓存容量必须 ≥ 单次请求工作集**，否则 LRU 抖动会让"看起来放满了"的缓存命中率归零。
6. **多线程拷贝会被 GIL 拖死**：4 线程 0.607 ms/专家 vs 4 独立进程 0.194 ms/专家 → **一卡一路必须独立进程**。
7. **别被首拷假象骗**（P2P 带宽、异步首次初始化都会给错觉）。
8. **"被限制"的结论必须实测**：`ulimit -l=8MB` 不限制 `pin_memory`（走 `hipHostMalloc`，实测 pin 8GB 成功）；
   容器里 `ss -ltn` 看不到端口 ≠ 服务挂了（用 `curl -sv` / urllib 验证）。
9. **`torch.cuda.synchronize()` 不带参数只同步当前设备** → 跨卡拷贝会测出 15TB/s 假数据。
10. **测速必须带真实 token 计数 + 注明 MTP**：3 块小样本 + MTP 抽双草能把 1.0 tok/s 显示成 3.7 tok/s。
11. **首个请求 ≠ 稳态**（Triton 首次编译 / 预冷缓存），**第 2 个请求才是真实速度**。
12. `multiprocessing` + CUDA/ROCm 必须 **spawn**；子进程要自己 `sys.path.insert`（否则静默 `No module named`，
    父进程卡在 `q.get()` 像"卡死"）；所有等待都要 `timeout` + 异常回传。
13. `pkill -f '[x]xxx'` 也要防自杀（脚本自己的路径含该模式就会杀到自己）；脚本里**不要** `pkill run_bg`。
14. **工具调用 >5 分钟会被打断** → 长任务一律 `setsid nohup ... &` 丢后台，再用短命令读结果文件。

## 附录 A. 另一条 AMD 线：本地聊天栈的 AMD 云 API 引擎（Qwen）

> 与本移植项目**不同**的另一条线，一并记录：日常聊天栈里的「AMD 引擎」= **AMD Radeon Cloud 官方 API**。

| 项 | 值 |
|---|---|
| 端点 | `https://developer.amd.com.cn/radeon/api/v1`（OpenAI 兼容） |
| 模型 | `Qwen3.8-Flash-Next`（支持看图 + 联网） |
| 预算 | $10 额度，用量本地记账（`amd_used`） |
| 实测延迟 | **约 2 tok/s，固定开销 ≈15 s**（60 token → 20.6 s；300 token → 26.1 s） |
| 对照 | 本机 35B（llama.cpp，8080）≈ **24 tok/s** |
| 用途 | 通过本地代理 `websearch_proxy.py`（8081）做**文字引擎三选一**：`local`（免费本地）/ `amd`（云 API）/ `deepseek`（官方 API）；`/api/switch_engine` 热切换，前端与 QQ 机器人共用同一开关 |
| 坑 | HTTP 400/404/413 时上游返回体不含 `choices` → 调用方必须显式报错而不是静默空回复；`max_tokens` 需锚定上限（`min(mt, 131072)`） |

**一句话**：AMD 云 API 便宜好用但**固定开销大、吞吐低**（≈2 tok/s），适合当"能看图 + 联网"的备用档；
本地 35B 才是主力（≈24 tok/s，免费）。
